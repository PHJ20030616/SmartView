## 4. 数据流

```
POST answers {questionId, answerText, requestId, durationSeconds?}
① 幂等查询 request_id → 命中直接返回既有结果
② 校验 会话存在/归属/IN_PROGRESS/questionId==current_question_id
③ 组装 AiEvaluateAnswerRequest（questionText/expectedPoints/stagePlan/roleDirection + sessionContext）
④ 事务外调 FastAPI /evaluate → 评估事实 + 追问候选(0-2)
⑤ mergeFollowUps 并入 Redis 候选池
⑥ getPool 取合并候选池（Redis → 5min 快照 → 同步重生成，降级不丢回答）
⑦ StagePolicyEngine.decide → nextAction/nextStage/selectedCandidate/decisionReason
⑧ 单事务：insert answer + 置当前题 ANSWERED + insert answer_evaluation(含快照)
      + insert 下一题(若未 FINISH) + 会话乐观锁推进/置 REPORTING
⑨ 事务提交后触发下一题 preGenerateAsync
⑩ 返回 {answerId, evaluation, nextQuestion, sessionStatus}
```

## 5. 幂等与并发（policy 4）

- 幂等查询先于题目校验：`SELECT ... WHERE request_id=? AND deleted=0`，并校验 sessionId 归属；命中返回该次回答的 evaluation + 下一题 + 会话状态。
- 乐观锁：`UPDATE interview_session SET version=version+1,... WHERE id=? AND version=?`；0 行 → 409。
- 双保险：`(question_id, deleted)` + `request_id` 唯一索引。
- 评估调用在事务外：避免 10s HTTP 占住 DB 连接/行锁；幂等+唯一索引兜底竞态。

## 6. StagePolicyEngine 规则（policy 2.4 顺序）

1. **硬终止**：总题量达 `total_max` → FINISH(QUESTION_LIMIT)；连续 3 题 score<30 且无要点 → FINISH(QUALITY_TOO_LOW)。
2. **阶段推进**：本阶段题量≥max → NEXT_STAGE；required 全覆盖且≥min → 可 NEXT_STAGE；全部满足且总题量≥min → FINISH(PLAN_COMPLETED)。
3. **深度限制**：`current_topic_follow_up_count`≥max 深度 → 禁 FOLLOW_UP。
4. **候选池空降级**：无候选 → NEXT_STAGE；下阶段也无 → FINISH(NO_VALID_QUESTION)。
5. **正常流程**：score≥70 有追问未超深 → FOLLOW_UP；40≤score<70 有换题 → SWITCH_TOPIC；score<40 有换题 → SWITCH_TOPIC；否则 NEXT_STAGE。

候选排序（policy 3.4）：追问 → 同阶段换题（优先 missing_topics）→ 下一阶段入口。

决策快照 `candidate_pool_snapshot_json`：顶层 `candidates` 数组（FollowUpPoolService 已按此读取）+ `decision`(nextAction/nextStage/selectedCandidateIndex/decisionReason/excluded) + `facts`。

## 7. 覆盖度更新

回答后更新当前阶段：`question_count+1`；topic 并入 `covered_topics`；`missing_topics=required-covered`；回答题为 FOLLOW_UP 则 `current_topic_follow_up_count+1` 否则归 0；NEXT_STAGE 初始化下一阶段覆盖项并更新 `current_stage`。

## 8. 错误处理

404 会话不存在 / 403 非本人 / 409 非 IN_PROGRESS、过期题、乐观锁冲突 / 评估失败→允许重试（不落库回答） / 候选池缺失→降级不丢回答。
