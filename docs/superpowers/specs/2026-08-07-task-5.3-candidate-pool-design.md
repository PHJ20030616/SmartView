# Task 5.3 — 候选问题池生成 设计文档

> 事实来源：`docs/interview-policy.md` 第 3 节、`develop_plan/smartview-task-plan_1.0.md` Task 5.3。
> 目标：建立候选问题池的生成、存储与重建机制，为 Task 5.4 的 `StagePolicyEngine` 提供决策输入。

## 1. 职责边界

- **FastAPI**：只生成候选问题（事实），不返回 `nextAction` / `nextStage` / `selectedNextQuestion`。
- **Spring Boot**：触发预生成（异步）、Redis 读写、快照重建；最终决策由 5.4 的 `StagePolicyEngine` 完成。

## 2. 已确认决策

| 决策点 | 结论 |
| --- | --- |
| 追问候选池职责边界 | 5.3 实现追问生成能力（独立接口验证），5.4 evaluate 图内联复用同一套节点 |
| 预生成异步机制 | Spring `@Async` + 专用线程池，非 MQ |
| 追问池存储 | 追问候选池也写入同一 Redis key（`candidateType=FOLLOW_UP`） |
| 能力结构 | 单一接口 `POST /api/v1/interview/candidate-pool` + 单一图，`poolType` 驱动 |

## 3. 架构与数据流

```
提问落库(afterCommit) → FollowUpPoolService.preGenerateAsync(@Async)
  → 调 FastAPI(PRE_GENERATED) → CandidatePoolRedisRepository.save
  → key: interview:candidate_pool:{sessionId}:{questionId}:{currentStage}, TTL 30min

回答提交(5.4接入) → evaluate 图内联复用 build_candidate_pool 节点 → mergeFollowUps 并入 Redis key
getPool(决策时) → 读 Redis → 缺失/过期/解析失败 → ①最近5min快照 ②同步调FastAPI ③空
```

## 4. AI 契约变更（`contracts/ai-api/openapi.yaml`）

新增 `POST /api/v1/interview/candidate-pool`（operationId `generateCandidatePool`）：

- `GenerateCandidatePoolRequest`：`sessionId`、`questionId`、`roleDirection`、`poolType[PRE_GENERATED|FOLLOW_UP]`、`stagePlan`(opaque)、`stageCoverage`(opaque)、`sessionContext{currentTopic, questionCount}`、`evaluationFacts{score, level, matchedPoints[], missingPoints[], riskPoints[], answerText, questionText}`(FOLLOW_UP 用)、`historyTopics[]`、`traceId`
- `CandidatePoolItem`：`questionText`、`topic`、`stage`、`candidateType[SAME_STAGE_SWITCH|NEXT_STAGE_ENTRY|FOLLOW_UP]`、`sourceType`、`expectedPoints[]`、`targetPoint`、`reason`
- `GenerateCandidatePoolResponse`：`success`、`candidates[]`、`errorMessage`

沿用现有 AI 契约约定：契约更新 → FastAPI 手写 Pydantic → 后端 `ai/client` 手写 DTO。web-api 契约不变。

## 5. FastAPI 候选池生成图

新增：`services/question_generator.py`、`nodes/stage_controller.py`、`nodes/generate_question.py`、`nodes/build_candidate_pool.py`、`graphs/candidate_pool_graph.py`；`api/v1/interview.py` 加端点。

| 节点 | 职责 |
| --- | --- |
| `stage_controller` | 确定性。PRE_GENERATED：同阶段换题（`required_topics − covered`，≤2 topic）+ 下一阶段入口（顺序 BASIC→PROJECT→SCENARIO 取下一阶段前 2；SCENARIO 无下一阶段）。FOLLOW_UP：深度门控（`current_topic_follow_up_count ≥ max_follow_up_depth` → 0 道）+ 得分门控（<40→0；40-70→1 缺口；>70 有亮点→1 深度）+ 风险追问（riskPoints 非空→1，合计≤2）。stageCoverage 为空视为全部未覆盖。 |
| `generate_questions` | 逐目标调 LLM（`question_generator` 复用 `call_deepseek_json`）。追问目标带 `basis`（缺失点/风险点/亮点）+ 当前题与回答。 |
| `build_candidate_pool` | 组装元数据、按 topic+questionText 去重、与 historyTopics 去重、封顶（PRE_GENERATED≤4，FOLLOW_UP≤2）。 |

**v1 取舍**：候选池不逐候选做知识检索，`sourceType` 由目标推断（BASIC→KNOWLEDGE_BASE、PROJECT→RESUME_PROJECT、SCENARIO→EXPERIENCE_CASE/MIXED）；正式被选中题目落库时仍走严格溯源。

## 6. 后端组件

- `infra/redis/CandidatePoolRedisRepository`：包装 `StringRedisTemplate`，`save/read/mergeFollowUps/delete`，Jackson 序列化，TTL 30min。
- `config/AsyncConfig`：`@EnableAsync` + `ThreadPoolTaskExecutor("candidatePoolExecutor")`（核心 2/最大 4/有界队列/CallerRunsPolicy）。
- `interview/model/CandidatePoolItem`：POJO，client DTO / Redis / 服务层共用。
- `interview/service/FollowUpPoolService`：
  - `preGenerateAsync(sessionId, questionId)`：@Async；加载 session → 组装 PRE_GENERATED 请求 → 调 `AiInterviewClient.generateCandidatePool` → 写 Redis；异常仅记日志。
  - `savePool(...)` / `mergeFollowUps(...)`：写/并入 Redis。
  - `getPool(sessionId, questionId, stage)`：读 Redis → 缺失/过期/解析失败 → ①最近 5min `answer_evaluation.candidate_pool_snapshot_json.candidates` ②同步调 FastAPI(PRE_GENERATED) 写回 ③空。
- `interview/mapper/AnswerEvaluationMapper`：新增（Task 5.1 未建）。
- `ai/client/AiInterviewClient`：新增 `generateCandidatePool` 方法 + 请求/响应 DTO。
- 触发点：`createSession` 事务提交后（afterCommit）调 `preGenerateAsync`（跨 Bean 使 @Async 生效）；5.4 每道新题走同一入口。

## 7. 快照格式约定（5.3 读取 / 5.4 写入）

`candidate_pool_snapshot_json` 顶层含 `candidates[]`（`CandidatePoolItem` 数组）与决策元数据；5.3 的 `getPool` 只读 `candidates`。

## 8. 错误处理与降级

| 场景 | 处理 |
| --- | --- |
| FastAPI 池生成超时/失败 | 记日志；决策时靠快照/同步重建兜底 |
| Redis 写失败 | 记日志继续（缓存可降级） |
| Redis 读缺失/解析失败 | 走 getPool 重建链 |
| 重建全部失败 | 返回空，StagePolicyEngine（5.4）按 policy 5.3 降级 |

## 9. 测试计划

- **FastAPI(pytest)**：`stage_controller` 目标计算（缺主题回退/最后阶段无下一阶段/深度门控/得分门控/风险封顶）；`candidate_pool_graph` 端到端（替身 LLM：封顶/去重/元数据）；`question_generator` 字段归一；端点鉴权+请求校验。
- **后端(JUnit)**：`FollowUpPoolServiceTest`（异步触发调 client+写 Redis；getPool 命中/快照重建/同步重生成/全失败）；`CandidatePoolRedisRepositoryTest`（save/read/merge/TTL）。

## 10. 验收对照

- [ ] 每次问题返回后 Redis 可见候选池 → `preGenerateAsync` + Redis
- [ ] 候选数量有上限 → `build_candidate_pool` 封顶（≤4 / ≤2）
- [ ] 候选标明来源与目标考察点 → `sourceType` + `targetPoint`
- [ ] 单一主题连续追问不超最大深度 → `stage_controller` 深度门控 + `stageCoverage.current_topic_follow_up_count`
